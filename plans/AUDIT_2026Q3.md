# 电商系统全面审查与整改方案

> 审查范围：`backend/`（46 个 API 路由文件、44 个测试文件 /129 用例、14 个 Alembic 迁移）、`frontend/`（33 个买家页 + 商家/管理后台）
> 审查基准：天猫、京东、亚马逊主流电商平台
> 结论摘要：本项目**功能广度已经很可观**（优惠券、积分、直播、分销、种草笔记、AR、预售、工单均已落地），核心资金链路的并发安全也做得比多数同类项目扎实。主要短板集中在 **① 游客不可浏览的致命转化漏斗断裂、② 前端工程化债务（巨型文件 / 静默吞错 / any）、③ 无障碍与移动端、④ 结算流程缺少独立确认页**。

## 一、代码质量问题

### 【致命】C-1 游客无法浏览任何页面，转化漏斗从入口断裂

- **现状描述**：`App.tsx` 中买家侧路由（含首页 `/market`、商详 `/product/:id`、搜索 `/search`）全部被 `ProtectedRoute` 包裹。`ProtectedRoute.tsx:18-28` 中未登录一律 `navigate("/login")`，且 `:35` `if (!user) return null`。任何未登录用户访问站点，看到的第一屏就是登录页。
- **对标参考**：天猫/京东/亚马逊均允许游客完整浏览商品、搜索、加购，**仅在结算时**才要求登录（亚马逊甚至支持 guest checkout）。登录墙前置是电商转化率的头号杀手，也直接摧毁 SEO（爬虫只能抓到登录页）。
- **整改建议**：
  1. 将 `/market` `/product/:id` `/search` `/shop/:id` `/discover` 移出 `ProtectedRoute`，改为公开路由。
  2. 加购、收藏、下单等**写操作**在触发时才拦截，弹出登录浮层（保留当前页面上下文，不整页跳走）。
  3. 游客购物车存 `localStorage`，登录后与服务端购物车合并。
  4. 保留 `state:{from}` 的原路返回能力（该逻辑已有，`ProtectedRoute.tsx:26`）。
- **优先级**：**P0（致命）** — 这是本项目对标电商平台最严重的单点缺陷。

### 【严重】C-2 静默吞错 29 处，故障不可观测

- **现状描述**：全前端 29 处 `.catch(() => {})`。典型如 `Market.tsx:413` `getBanners().then(setBanners).catch(onLoadFail("banners"))` 之外，仍有大量裸吞。接口失败后页面呈现"空白但无提示"，用户不知发生了什么，开发者也拿不到线索。
- **对标参考**：主流平台模块级失败会降级为"加载失败，点击重试"，而非静默留白。
- **整改建议**：统一走 `AsyncBoundary`（已存在）；确需忽略的错误必须写成 `.catch((e) => reportSilently(e, 'banners'))` 上报 Sentry，禁止空函数体。加 ESLint 规则 `no-empty-function` 限定 catch。
- **优先级**：P1（严重）

### 【严重】C-3 `api/index.ts` 57.7KB 巨型模块

- **现状描述**：单文件承载全站所有接口方法与类型定义，是全项目最大文件。任何接口改动都触碰同一文件，多人协作必冲突；且无法 tree-shaking，首屏包体被拖大。
- **对标参考**：中大型前端按域拆分 `api/product.ts` `api/order.ts` `api/cart.ts`…
- **整改建议**：按业务域拆为 12~15 个模块，`api/index.ts` 仅做 re-export 保持兼容，可分批无痛迁移。类型定义抽到 `api/types/`。
- **优先级**：P1（严重）

### 【一般】C-4 类型安全与调试残留

- **现状描述**：`any` 类型 35 处；`console.log` 残留 25 处（生产构建未清除，可能泄露业务数据到浏览器控制台）。
- **整改建议**：`any` 逐步替换为真实类型或 `unknown` + 收窄；`vite.config.ts` 配置 `esbuild.drop: ['console','debugger']`（生产），并加 ESLint `no-console`（allow warn/error）。
- **优先级**：P2（一般）

### 【一般】C-5 部分金额字段仍用 `Float`

- **现状描述**：主链路已用 `Numeric(12,2)`，但 `models/affiliate.py`、`models/invoice.py`、`models/shipping.py` 中金额字段仍为 `Float`。分销佣金按比例计算后累加，二进制浮点误差会随结算周期累积。
- **对标参考**：所有涉及资金的字段必须定点数。
- **整改建议**：三处改 `Numeric(12,2)`，配套写一个 Alembic 迁移做类型转换与存量数据 round 修正。
- **优先级**：P2（一般，但属资金正确性，建议尽快）

### 【一般】C-6 `_ensure_demo_columns` 与 Alembic 双轨并存

- **现状描述**：`main.py:88-146` 维护 57 条 `ALTER TABLE` 兜底，注释已说明"列演进已由 0009 迁移正式接管，此处仅作兜底"（`main.py:255-257`）。但双轨长期并存会导致"迁移没写全也能跑起来"，掩盖迁移缺失，且启动期额外开销。
- **整改建议**：设开关 `ALLOW_SCHEMA_AUTOFIX`，仅本地/演示为 True，生产 False；CI 增加"用纯 Alembic 建库后跑全量测试"的任务，确保迁移自洽后即可删除该兜底。
- **优先级**：P2（一般）

## 二、用户体验问题

### 【致命】U-1 无独立"确认订单"页，结算塞在购物车侧栏

- **现状描述**：`Cart.tsx` 中结算区是右侧 `Card`（`:550` `title={t("cart.checkoutTitle")}`），地址选择、金额、下单按钮（`:752`）全挤在购物车页。
- **对标参考**：天猫/京东/亚马逊都有独立的**确认订单页**（`/checkout`），承载：收货地址（含默认地址卡片+新增）、配送方式与时效、发票信息、优惠券选择、积分抵扣、支付方式、费用明细（商品小计/运费/优惠/实付逐行展示）、最终"提交订单"。这是用户建立支付信任的关键一步。
- **整改建议**：新建 `/checkout` 页，购物车"去结算"跳转至此；实现完整费用明细逐行拆解；下单成功进入 `/pay`（该页已存在）。同时补 **购物车 → 确认订单 → 支付 → 成功** 的四步进度条。
- **优先级**：**P0（致命）**

### 【严重】U-2 无障碍近乎为零

- **现状描述**：全前端仅 3 处 `aria-*` 属性。图标按钮无 `aria-label`，弹窗无焦点管理，键盘用户与读屏用户基本无法使用。
- **对标参考**：亚马逊严格遵循 WCAG 2.1 AA。国内平台也在合规推进。
- **整改建议**：图标按钮补 `aria-label`；Modal 补焦点陷阱与 Esc 关闭；表单 `label` 与控件 `htmlFor` 绑定；保证键盘 Tab 可达主流程；颜色对比度校验至 4.5:1。
- **优先级**：P1（严重）

### 【严重】U-3 商详页缺少决策关键信息

- **现状描述**：`ProductDetail.tsx` 已有评价（`ProductReviews`）、问答（`ProductQA`）。但缺少：促销叠加后的**到手价**试算、运费与预计送达时间、库存紧张提示、服务承诺（7 天无理由/正品保障）、规格选择后的图片联动。
- **对标参考**：京东商详"预计明天送达"与到手价是核心转化要素。
- **整改建议**：商详补"到手价"计算模块（叠加券后价）、配送时效预估、服务承诺图标组、SKU 选择联动主图与库存。
- **优先级**：P1（严重）

### 【一般】U-4 首页分类浏览态砍掉过多模块

- **现状描述**：`Market.tsx:219` `browsingCategory = Boolean(cat)`，一旦选中分类，轮播、快捷入口、榜单、推荐（`:460,:482,:543,:577`）全部隐藏。
- **对标参考**：主流平台分类页仍保留"该类目热销榜/相关推荐"，维持逛的连续性。
- **整改建议**：分类态隐藏轮播即可，保留并替换为**类目内**榜单与推荐；补面包屑 `首页 > 类目 > 子类目`。
- **优先级**：P2（一般）

### 【一般】U-5 缺少全局购物车角标与跨页状态反馈

- **整改建议**：顶部导航常驻购物车图标 + 数量角标，加购时飞入动画与 Toast，形成即时正反馈。
- **优先级**：P2（一般）

## 四、视觉与内容

- **V-1 信息层级**：首页模块权重平均，缺少视觉锚点。建议按"轮播 → 秒杀（强时间压迫感）→ 类目直达 → 榜单 → 个性化 feed"建立递进层级，秒杀区用高饱和色 + 倒计时强化紧迫感。（P2）
- **V-2 价格排版**：电商中价格是第一视觉元素。建议统一价格组件：符号小、整数大、小数小，划线原价灰色弱化，优惠标签红底白字。（P2）
- **V-3 移动端**：需确认断点覆盖，商详"加入购物车/立即购买"在移动端应为**吸底双按钮**。（P1）
- **V-4 文案调性**：错误文案避免"请求失败"这类技术语言，改为"网络开小差了，点击重试"；空状态给出下一步行动（"购物车还是空的 → 去逛逛"，`EmptyState` 已有组件，补齐引导按钮即可）。（P2）
- **V-5 图片体验**：商品图统一 `aspect-ratio` 防抖动，接入 WebP 与 `loading="lazy"`，主图支持放大镜。（P2）

## 五、技术债务

- **T-1 前端巨型文件**：`api/index.ts` 57.7KB 及若干 400+ 行页面组件，拆分为 hooks（数据）+ 展示组件。（P1）
- **T-2 测试结构性失衡**：后端 129 用例覆盖良好，**前端仅 2 个测试文件**（`utils/__tests__/cart.test.ts`、`nextActions.test.ts`）。核心链路无测试。建议补：加购→结算→支付的 E2E（Playwright），以及购物车金额计算、优惠叠加的单测。（P1）
- **T-3 双轨 schema 管理**：见 C-6。（P2）
- **T-4 SQLite 生产隐患**：默认 `sqlite+aiosqlite`，写并发能力弱，行锁语义与 PostgreSQL 有差异。生产必须 PostgreSQL，并在 PG 上跑一遍并发下单压测验证锁行为。（P1）
- **T-5 可观测性**：有 `inc_counter` 埋点基础，但缺统一 APM、结构化日志与 traceId 贯穿。建议接入 OpenTelemetry + Sentry。（P2）
- **T-6 缓存缺位**：首页轮播、类目、榜单等高频只读数据每次查库。建议 Redis 缓存 + 缓存失效策略。（P2）

## 七、建议的推进顺序

**第一批 T1~T5 是分水岭**。当前状态下，一个未登录的访客打开站点只能看到登录页——无论后台功能多完善，它都还不像一个电商平台。这 5 项完成后，项目才真正具备"电商"的基本形态，之后的 P1/P2 才是在打磨体验与质量。

技术底子（并发安全、资金精度、迁移、测试）已经不错，**不需要推倒重来**，整改集中在前端体验层与工程化，风险可控。
